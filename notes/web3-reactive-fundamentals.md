# Web3 基础与 Reactive 原理笔记

> 面向 Web3 新人，配合 ETHPanda × Reactive Builder Camp 学习。Reactive 相关内容对照了模板仓库 [ethpanda-org/reactive-builder-camp](https://github.com/ethpanda-org/reactive-builder-camp) 的 `starter/` 合约、`docs/cheatsheet.md` 和 `docs/faq.md`。

## 总纲

这 8 个问题都挂在一条主线上：**每条区块链都是一个独立、封闭、被动的账本。**

- **独立封闭**：链和链之间互相看不见，所以才需要跨链和跨链桥；同一个币在不同链上价格可以不一样，所以才有跨链套利。
- **被动**：合约自己不会动，所以过去要自己写机器人盯链，现在 Reactive 把这件事搬到了链上。

下面按「先底层、后上层」的顺序讲。

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 不同的链 | 每条链就是一个独立的区块链网络，不能直接通信，代币也不能直接转过去 |
| 2 | 出块 | 定期把一批交易排好顺序、打包，让全网对「谁先谁后」达成一致 |
| 3 | 交易全流程 | 私钥签名授权 → 全网各自验证、排序、执行 → 共识确认结果 |
| 4 | 跨链 / 跨链桥 | 让 B 链「相信」A 链上发生了某件事。难点不在「搬消息」，而在「凭什么信」 |
| 5 | Reactive 是什么 | 一条独立的 EVM 区块链（平台），不是框架。补的是合约「不会主动执行、看不到别的链」两个短板 |
| 6 | 三步流程 | 三条链上的三笔独立交易，彼此异步，不保证同时成功 |
| 7 | 跨链套利 | 各链的池子各自定价，把价差拉平需要时间和成本，这段空档就是利润 |
| 8 | 巨鲸 / 聪明钱 | 利用链上账本完全公开做数据分析：一个看「钱多」，一个看「历史上赚得多」 |

## 1️⃣ 不同的链：是什么、为什么这么多、能不能互通

**结论**：是的，每条「链」就是一条独立的区块链，也可以理解成一个独立的网络。它有自己的节点、账本、共识和原生币。链和链之间互相看不见，不能直接通信。

### 常见的链

| 类型 | 例子 | 特点 |
|---|---|---|
| 比特币 | Bitcoin | 最早的链。主要用来转账，几乎不能写复杂合约。约 10 分钟出一个块 |
| 以太坊主链（L1） | Ethereum | 智能合约的鼻祖，跑 EVM（以太坊虚拟机）。12 秒出一个块。安全，但手续费贵 |
| 以太坊二层（L2 / Rollup） | Arbitrum、Optimism、Base、Unichain | 交易在 L2 上执行，结果压缩后交回以太坊存证。又快又便宜，安全性部分借用以太坊 |
| 其他兼容 EVM 的 L1 | BNB Chain、Avalanche、Sonic、**Reactive** | 能跑以太坊的合约代码，但共识自己做，和以太坊无关 |
| 不兼容 EVM 的 L1 | Solana、Sui、Aptos | 虚拟机和编程语言都不一样（Rust、Move） |
| 测试网 | Sepolia、Base Sepolia、Lasna | 主网的「练习场」，币不值钱。本营全程用测试网 |

### 为什么要有这么多链？

根源是**区块链不可能三角**：去中心化、安全、性能，三者很难同时做到极致，每条链只能选一种取舍。

- **以太坊**选了去中心化 + 安全：全球大量节点都要把每笔交易重新执行一遍，所以每秒只能处理十几笔，手续费（gas）贵。
- **Solana**选了性能：对节点硬件要求很高，能跑节点的人就少一些。
- **L2** 是折中方案：在自己链上执行交易，换来快和便宜；再把结果交回以太坊存证，借用以太坊的安全。

除了技术取舍，还有商业原因：项目方想要自己的生态、自己的代币、自己的手续费收入，所以链越来越多。

👉 可以这样类比：每条链是一家独立银行的账本系统。招行的账本不知道工行那边发生了什么。

### 为什么链和链不能直接通信？

1. **共识只对自己负责**。以太坊的验证者只验证以太坊自己的区块。要让以太坊上的合约「相信」Base 上发生了某件事，它得能验证 Base 的区块，可合约里既没有 Base 的节点，也没有现成的办法去验证 Base 的共识。
2. **合约不能发网络请求**。EVM 是一个「确定性沙盒」：全网节点执行同一笔交易，必须得到完全相同的结果。如果合约能去请求别的链，不同节点在不同时刻可能拿到不同答案，共识就崩了。所以合约只能读本链的数据。
3. **没有共同的时钟，也没有「原子性」**。两条链各出各的块，不存在「两边要么都成功、要么都失败」的跨链事务。

### 各链的协议一样吗？能直接转代币吗？

**协议要分层看。**

- **节点通信和共识算法**：每条链都不一样。
- **虚拟机**：兼容 EVM 的链之间（以太坊、Base、BNB 等），合约代码基本能原样部署，地址格式也相同。比特币、Solana 这类链则完全不同。

⚠️ **新手最常踩的坑**：同一个私钥，在所有 EVM 链上算出来的是**同一个地址**，但每条链上的余额**互相独立**。你在 Sepolia 上有 ETH，不代表 Base Sepolia 上也有。营里 FAQ 第 2 题说的就是这个：有人把币转到了错误的链上。

**代币不能直接转。** 代币本质上只是某条链上某个合约里的一行记录，比如 `balances[你的地址] = 100`，它不是一个能「搬走」的东西。所谓「把 USDC 从以太坊转到 Base」，实际是两步：先在以太坊上锁住或销毁，再在 Base 上铸造或释放等量的币，中间由跨链桥来协调（见第 4 节）。

### 多链的弊端

| 弊端 | 说明 |
|---|---|
| 流动性碎片化 | 同一种币分散在十几条链上，每个交易池都变浅，大单更容易把价格打偏。这也是跨链套利存在的原因 |
| 使用体验差 | 要管好几种 gas 币、好几套网络配置，转错链可能直接丢钱 |
| 安全风险 | 跨链桥是黑客最喜欢的目标。2022 年 Ronin（约 6.25 亿美元）、Wormhole（约 3.2 亿美元）、Nomad（约 1.9 亿美元）都是桥被攻破 |
| 不保证同时成功 | 一次跨链操作其实是两笔独立的交易，可能一边成功、一边失败 |

## 2️⃣ 出块：是什么、为什么需要、快慢由什么决定

**结论**：**区块 = 一批排好顺序的交易 + 一个记录「上一个块是谁」的块头。** 出块的根本目的，是让成千上万个互不信任的节点，对「交易的先后顺序」达成一致。

### 为什么要按「块」确认，而不是一笔一笔确认？

1. **防止双花（同一笔钱花两次）**。比如你只有 1 ETH，却同时给 A 和 B 各发一笔「转出 1 ETH」。世界各地的节点收到这两笔交易的先后可能不同。必须有一个全网公认的顺序，后面那笔才会因为余额不足而失败。区块就是这个「官方顺序」。
2. **批量处理更划算**。全网每达成一次共识，都要来回通信好几轮，耗时几百毫秒到几秒。每笔交易单独来一次太贵了；几百笔打包成一块、只做一次共识，成本就摊薄了。
3. **防止篡改**。每个块头里都存着上一个块的哈希（可以理解为指纹）。只要改掉历史上任意一笔交易，那个块的哈希就会变，后面所有块都得重新计算、重新获得全网认可，实际上做不到。这条首尾相连的哈希链，就是「区块链」名字的由来。

一个区块里有什么（以以太坊为例，简化版）：

```
Block #N
├── parentHash    上一个块的哈希，块和块靠它串成链
├── stateRoot     执行完本块后，全部账户状态的「指纹」
├── receiptsRoot  本块所有交易回执的指纹（事件日志在回执里）
├── timestamp / number / gasUsed / baseFee ...
└── transactions[]  排好顺序的交易列表
```

### 影响出块速度的因素

| 因素 | 为什么有影响 |
|---|---|
| 共识机制 | 比特币用工作量证明（PoW），靠算力解题，难度被调到平均约 10 分钟一块。以太坊用权益证明（PoS），按固定时间槽轮流出块，每槽 12 秒 |
| 网络传播延迟 | 新块必须在下一块出来之前传遍全球节点。节点越多、分布越广，就要留越长的时间，否则经常分叉 |
| 中心化程度 | L2 通常只有一个「排序器」负责出块，不用和别人商量，所以能做到 1 秒甚至 200 毫秒（比如 Base Sepolia、Unichain Sepolia）。代价是中心化 |
| 区块大小 / gas 上限 | 块越大，执行和传播就越慢 |
| 节点硬件 | Solana 约 400 毫秒出一块，靠的是高性能硬件 |

Reactive 约 1 秒出一块。

⚠️ **「出块」和「最终确定」是两回事**：

- **出块**：交易被打包进了一个块，但这个块还有可能被回滚（叫 reorg，链重组）。
- **最终确定（finality）**：再也不可能被回滚。以太坊大约要 2 个 epoch，也就是约 13 分钟。
- 这一点对赛道 1 很关键：赛道 1 评的是「源链事件 → Reactive → 回调」的端到端延迟，每一段都受所在链的出块速度影响。FAQ 第 19 题要求你记录三个区块的时间戳，原因就在这里。

## 3️⃣ 一笔链上交易的完整流程

**结论**：一笔交易就是一条「我授权做某件事」的签名消息。私钥签名证明确实是你本人授权的；全网节点各自验证、排序、执行，最后通过共识确认同一个结果。整个过程不需要信任任何一方。

下面以「在 Sepolia 上调用 `CampOrigin.ping(100)`」为例：

```
① 构造 → ② 签名 → ③ 广播 → ④ 进内存池 → ⑤ 打包排序 → ⑥ 执行 → ⑦ 出块传播 → ⑧ 全网重新验证 → ⑨ 最终确定
```

| 步骤 | 发生了什么 | 为什么这样设计 |
|---|---|---|
| ① 构造 | 钱包填好各个字段：`chainId`（链编号）、`nonce`（账户交易序号）、`to`（合约地址）、`value`（转多少币）、`data`（调用哪个函数、传什么参数）、gas 上限和愿意出的价格 | `chainId` 防止这笔签名被拿到别的链上重放。`nonce` 保证交易按顺序执行，也防止同一笔被重复提交 |
| ② 签名 | 用私钥对交易内容签名，得到一个签名值 | 任何人都能用签名反推出你的地址来验证，但反推不出私钥。所以**私钥就是账户的全部控制权**，泄露就等于被盗。营里反复强调「私钥不要给任何人和 AI」，原因就在这里 |
| ③ 广播 | 通过 RPC 服务发给某个节点，节点再点对点转发给其他节点 | 没有中心服务器，任何节点都能接收 |
| ④ 内存池 | 节点先做初步检查：签名对不对、nonce 对不对、余额够不够付 gas。通过后放进「待处理交易池」（mempool） | 内存池是公开的，别人能看到你还没上链的交易，所以会出现「抢跑」（MEV） |
| ⑤ 打包排序 | 这个时间槽被选中的验证者挑出交易、排好顺序，通常小费高的优先 | 区块空间有限，gas 费就是竞价：出价高的先上链 |
| ⑥ 执行 | 在 EVM 里逐笔执行：修改余额和合约存储，扣 gas，生成交易回执，回执里包含事件日志 | `emit Ping(...)` 就是在这一步产生的。⚠️ **事件只写在回执里，不属于合约状态，其他合约读不到**。这正是 Reactive 要存在的关键原因（见第 5 节） |
| ⑦ 出块传播 | 把交易列表和新的状态指纹打包成块，广播出去 | |
| ⑧ 全网重新验证 | 其他验证者收到块后，**自己再执行一遍**，比对算出的状态指纹是否一致，一致才投赞成票 | 「不信任，自己验证」：不用相信出块的人。作弊的块会被拒绝，出块者押上的保证金还会被罚没 |
| ⑨ 最终确定 | 拿到三分之二以上质押票数的检查点被确认为最终状态 | 之后想回滚，就得让全网至少三分之一的质押被罚没，经济上不可行 |

两个容易被忽略的点：

- **失败的交易也要付费**。交易报错（revert）后，状态会恢复原样，但已经用掉的 gas 照样扣，因为节点确实花了算力。速查表里「react() 里 revert 照样收费，要用 return 过滤」，是同一个道理。
- **交易哈希就是凭证**。拿它去区块浏览器，能查到这笔交易在第几个块、执行结果、产生了哪些事件。交营里的作业、提交黑客松，都要用它。

## 4️⃣ 跨链：为什么需要、怎么实现、跨链桥是什么

**结论**：跨链就是**让 B 链「相信」A 链上发生了某件事，并据此采取行动**。因为链之间互相看不见，必须有人把 A 链的消息搬到 B 链，还要让 B 链能验证这条消息是真的。跨链桥就是专门做这件事的一套合约加链下服务。**难点从来不在「搬」，而在「凭什么信」。**

### 什么场景需要跨链

| 场景 | 例子 |
|---|---|
| 转移资产 | 把 ETH 从以太坊转到 Base，享受更低的手续费 |
| 追逐收益 | Arbitrum 上借贷利率更高，把 USDC 挪过去 |
| 跨链套利 | 同一个币在两条链上价格不同（见第 7 节） |
| 跨链应用 | 在 A 链质押、在 B 链领奖励；多条链的治理投票汇总统计 |
| 跨链自动化 | A 链上发生某件事，自动触发 B 链上的操作。这正是 Reactive 做的事 |

### 怎么让 B 链「相信」？四种方式

越往下越不需要信任某个人，但实现也越难。

| 方式 | 原理 | 代表 | 你信任的是谁 |
|---|---|---|---|
| 多签中继 | 几个人看到 A 链的事件后签名，B 链合约认这些签名 | 早期很多桥、Ronin | 签名的人不作恶、私钥不被盗 |
| 外部验证者网络 | 一组独立节点各自观察 A 链，然后投票 | Wormhole、LayerZero、Chainlink CCIP | 大多数节点诚实 |
| 轻客户端 / ZK 证明 | B 链合约直接验证 A 链的区块头和数学证明 | IBC、各类 ZK 桥 | 只信数学和两条链本身 |
| Rollup 官方桥 | L2 提币回 L1 时，靠欺诈证明（有 7 天挑战期）或有效性证明 | Arbitrum、Optimism 官方桥 | 继承以太坊的安全，但慢 |

Reactive 的思路和第二类相近：Reactive 网络的节点同时跟踪各条源链，把事件送进 Reactive 链，再把回调交易投递到目标链。你信任的是 Reactive 网络本身。

### 资产是怎么「过去」的：三种模式

- **锁定 + 铸造**：在 A 链把原币锁进桥合约，在 B 链铸造等量的「包装币」。包装币的价值完全依赖桥里锁着的原币，桥一旦被盗，包装币就成了废纸。
- **销毁 + 铸造**：币的发行方自己控制多条链上的铸造权，在 A 链销毁、在 B 链增发。比如 Circle 对 USDC 的跨链方案（CCTP）。
- **流动性网络**：两边都有资金池，中继者先在 B 链把钱垫付给你，再去 A 链收回你锁的钱。速度快，比如 Across。

### 伪代码：一个最简单的「锁定 + 铸造」桥

```solidity
// ===== A 链（源链）=====
contract BridgeA {
    uint256 public nonce;
    event Locked(address user, uint256 amount, uint256 dstChainId, uint256 nonce);

    function lock(uint256 amount, uint256 dstChainId) external {
        token.transferFrom(msg.sender, address(this), amount);   // 1. 把用户的币锁进桥合约
        emit Locked(msg.sender, amount, dstChainId, nonce++);    // 2. 发出事件：有人要过桥
    }
}

// ===== 链下中继者（Relayer，一个后台程序）=====
loop:
    logs = A_RPC.getLogs(BridgeA, "Locked")          // 3. 持续监听 A 链上的 Locked 事件
    for log in logs:
        wait_until_finalized(log.blockNumber)         // 4. 等 A 链最终确定，防止链重组后锁币交易消失
        sig = sign(relayerKey, hash(log.user, log.amount, log.nonce, A_CHAIN_ID))
        B_RPC.send(BridgeB.mint(log.user, log.amount, log.nonce, sig))   // 5. 去 B 链提交铸币请求

// ===== B 链（目标链）=====
contract BridgeB {
    mapping(uint256 => bool) public processed;
    address public relayer;

    function mint(address user, uint256 amount, uint256 srcNonce, bytes calldata sig) external {
        require(!processed[srcNonce], "already minted");     // 6. 防重放：同一笔只铸一次
        require(recover(hash(user, amount, srcNonce, A_CHAIN_ID), sig) == relayer, "bad sig");
                                                              // 7. 验证消息确实来自可信的中继者
        processed[srcNonce] = true;
        wrappedToken.mint(user, amount);                      // 8. 给用户铸造包装币
    }
}
// 回程：在 B 链销毁包装币 → 中继者转达 → A 链解锁原币
```

几个关键点：

- **第 4 步为什么要等「最终确定」**：如果 A 链发生回滚，锁币交易就消失了，币回到用户手里；可 B 链已经铸了币，等于凭空多出一笔钱。
- **第 7 步是整个桥的命门**：中继者的私钥一旦被盗，攻击者就能随意铸币。Ronin 被盗，就是 9 个验证者私钥里有 5 个落入了攻击者手中。
- **对照 Reactive 的模板**：`CampOrigin` 对应第 1、2 步（发出事件）；Reactive 网络替你做了第 3 到 5 步的中继工作；`CampCallback` 里的两道检查 `onlyServiceProvider` 和 `onlyCallbackSender`，就是第 7 步的身份验证。区别在于，你不用自己跑中继服务器。

## 5️⃣ Reactive 是框架还是平台？解决什么问题？

**结论**：**Reactive Network 是一条独立的、兼容 EVM 的区块链，属于平台 / 基础设施，不是框架。** 它配套的 `reactive-lib-omni` 才是开发库（相当于 SDK）。它补的是智能合约天生的两个短板：**不会主动执行**，**看不到别的链**。

| 组成部分 | 是什么 | 类比 |
|---|---|---|
| Reactive 主网（chainId 1597）/ Lasna 测试网（chainId 5318007） | 一条独立的链，原生币是 REACT，约 1 秒出一块 | 一个云平台 |
| 系统合约 `SYSTEM`（地址 `0x8888…8888`） | 订阅事件、请求回调、扣费的统一入口 | 平台的 API |
| Callback Proxy（官方部署在各条目标链上） | 负责把回调送到你的合约 | 平台在各地的投递站 |
| `reactive-lib-omni` | 提供 `AbstractReactive`、`AbstractCallback` 等基础合约 | SDK |

### 为什么合约「不会自己动」？

以太坊上每笔交易，都必须由一个**有私钥的外部账户（EOA）签名并付 gas** 才能发起（见第 3 节）。合约没有私钥，只能等别人来调用它。所以以太坊上天然没有这三样东西：

- **定时器**：不存在「每天 0 点自动执行」这种机制。
- **事件监听**：合约 A 发出的事件，合约 B 根本读不到，因为事件只写在回执里，是给链下程序看的。
- **跨链读取**：合约不能发网络请求（见第 1 节）。

于是传统做法是自己写机器人：

```
自己的服务器上跑程序 → 不停轮询 RPC 盯着事件 → 判断条件 → 用服务器上的私钥签名发交易
```

问题也很明显：服务器会宕机；私钥放在服务器上有被盗风险；要 7×24 小时运维；判断逻辑在链下，别人看不见，也没法验证。

### Reactive 的思路：从「主动去拉」变成「等它推过来」

- **传统做法**：你的程序主动去轮询数据。
- **Reactive 的做法**：你写一个合约，提前向网络登记「我要听哪条链上的哪个事件」。事件一发生，网络就主动调用你合约里的 `react()`。

这和后端开发里的「轮询 vs Webhook」是同一回事。可以把 Reactive 理解成 **去中心化、能跨链的「Webhook + 规则引擎 + 执行器」**。

| 方案 | 怎么做 | 区别 |
|---|---|---|
| 自己写机器人 | 链下服务器 | 中心化，要自己运维 |
| Chainlink Automation / Gelato | 一组链下节点按时间或条件调用你的合约 | 主要做定时和条件触发，判断逻辑多数在链下 |
| **Reactive** | 判断逻辑写在 Reactive 链上的合约里，由事件驱动，原生支持跨链回调 | 逻辑在链上，公开可审计 |

需要客观说明：用 Reactive 省掉了你自己的服务器，但信任转移到了 Reactive 网络身上，由它负责观察源链和投递回调。

### 能解决什么问题

就是开营 PPT 里那张表：链上监控、定时任务、钱包保护、止损止盈和再平衡、跨链套利、AI Agent。它们的共同模式是：**某处发生了 X → 判断条件 Y → 去某处执行 Z**。

## 6️⃣ 深入讲「事件 → react() → 回调」三步流程

**结论**：一次完整的联动，是**三条链上的三笔独立交易**，由三方分别发起：

- 源链上那笔，由用户（或任意合约）发起；
- Lasna 上那笔，由 Reactive 网络发起；
- 目标链上那笔，由 Reactive 网络通过 Callback Proxy 发起。

下面结合模板仓库 `starter/` 里的真实代码来讲。

```
  源链 Sepolia                  Reactive 链 Lasna                       目标链 Base Sepolia
┌──────────────┐  ① Tx1     ┌───────────────────────┐   ③ Tx3       ┌────────────────────────┐
│ CampOrigin   │──emit────▶ │ 节点跟踪源链，匹配订阅表   │──请求回调───▶ │ Callback Proxy（官方）   │
│ ping(100)    │  Ping事件   │      ↓ ② Tx2           │               │   ↓ 改写第 1 个参数       │
└──────────────┘            │ CampReactive.react()  │               │ CampCallback.onEvent() │
                            │ 判断 value >= 阈值      │               │ 执行动作，emit Handled   │
                            └───────────────────────┘               └────────────────────────┘
   用户付 Sepolia ETH          合约余额付 lREACT                       回调合约付目标链 ETH
```

### 第 0 步：订阅（在部署时完成）

```solidity
SYSTEM.subscribe(originChainId_, originContract_, originTopic0_,
                 REACTIVE_IGNORE, REACTIVE_IGNORE, REACTIVE_IGNORE);
```

意思是：「请帮我盯着链 11155111（Sepolia）上这个合约地址，只要它发出 topic0 等于 `keccak256("Ping(address,uint256)")` 的事件就通知我，其余条件不限。」

- **为什么按 topic0 来订阅**：EVM 里一条事件日志由 `topics[0..3]` 和 `data` 组成。
  - `topic0` 是事件签名的哈希，用来区分是哪种事件；
  - 带 `indexed` 的参数放在 topic1 到 topic3，可以被过滤；
  - 不带 `indexed` 的参数打包进 `data`，不能被过滤。
- **为什么订阅只支持「等于」匹配**：节点要对每条链、每个区块里的海量日志做匹配。只做「等于」匹配可以建哈希索引，一查就中。如果允许 `value > 100` 这种范围条件，就得对每条日志跑一段任意逻辑，成本没法控制。所以分工是：**订阅做粗过滤，`react()` 做细判断**。
- 订阅信息存在节点里，合约自己读不回来，要自己记好订阅时用的参数。

### 第 1 步：事件（源链）

```solidity
function ping(uint256 value) external { emit Ping(msg.sender, value); }
```

- 你用钱包调用 `ping(100)`，这是一笔普通的 Sepolia 交易（Tx1），完整走一遍第 3 节的流程。
- 它产生一条日志：`{合约地址: CampOrigin, topic0: Ping 签名的哈希, topic1: 你的地址, data: 100 的编码}`。
- 真实项目里，这一步通常不用你自己部署，而是直接监听别人已有的合约，比如 Uniswap 交易池的 `Swap` 事件、ERC-20 代币的 `Transfer` 事件。**源链合约完全不需要知道 Reactive 的存在**，所以任何已经上线的协议都能被监听，这是一个很大的优势。

### 第 2 步：反应（Reactive 链）

Reactive 节点跟着源链出块，读到这条日志，发现它命中了订阅，于是在 Lasna 上生成一笔系统交易（Tx2），调用 `CampReactive.react(LogRecord)`。

```solidity
function react(LogRecord calldata log_) external onlySystem {
    if (log_.topic0 != ORIGIN_TOPIC_0) return;                    // 防御性检查：确认是要处理的事件
    uint256 value = abi.decode(log_.data, (uint256));             // 从 data 里解出数值
    if (value < threshold || recipient == address(0)) return;     // 真正的条件判断（就是「Y」）
    ...
    SYSTEM.requestCallbackV_1_0(CallbackConfiguration_V_1_0({chainId, recipient, gasLimit, payload}));
}
```

- **为什么要加 `onlySystem`**：只允许系统合约调用 `react()`。否则任何人都能伪造一条「源链事件」来骗你的合约。
- **为什么用 `return` 而不用 `revert`**：Tx2 已经执行了，gas 已经花掉，revert 照样扣 lREACT。
- **费用从哪扣**：从合约自己的 lREACT 余额里扣（部署时随交易转进去的）。余额不够就会产生欠款（debt），欠款大于 0 时合约会**静默停止**，收不到任何事件。
  - 为什么这样设计？这笔交易不是你签名发起的，网络没法从你的钱包扣钱，只能从合约账户扣。这也防止有人靠海量订阅白嫖网络算力。
- **Reactive 合约有自己的状态**：`remaining`、`threshold` 这些变量都存在 Reactive 链上，所以能写「累计 3 次大额转账才报警」这种需要记忆的逻辑。这是比普通 Webhook 更强的地方。

### 第 3 步：回调（目标链）

Reactive 网络收到回调请求后，在目标链上向 **Callback Proxy** 发一笔交易（Tx3），Proxy 再去调用你的 `CampCallback.onEvent(...)`。

这个函数上有两道检查，缺一不可：

```solidity
function onEvent(address reactive_, ...) external
    onlyServiceProvider            // 调用者必须是本链官方的 Proxy，防止任何人直接调用你的函数
    onlyCallbackSender(reactive_)  // 第 1 个参数必须是你认可的那个 Reactive 合约，防止别人的 Reactive 合约借 Proxy 来调你
```

- **为什么 payload 的第一个参数要填 `address(0)`？**
  - 在目标链上，调用你合约的永远是 Proxy，你的合约没法知道「到底是哪个 Reactive 合约发起的请求」。
  - 所以网络在投递时，会把第一个参数**强制改写**成真正发起请求的 Reactive 合约地址。
  - 如果这个值允许你自己填，攻击者就能部署一个自己的 Reactive 合约，在里面冒填你的地址来冒充你。所以只能由网络来写，你填什么都会被替换，`address(0)` 只是占个位置。
  - 这就是第 4 节伪代码里第 7 步「验证消息来源」在 Reactive 里的实现方式。
- **回调的费用谁付**：由**回调合约自己**在目标链上用 ETH 支付，所以部署时要带上 ETH。
  - 原因：Reactive 网络并不持有你在目标链上的 ETH，而 Tx3 的 gas 必须有人在目标链上付。由接收方付最合理：你的合约愿意接收这个回调，就为它买单。
  - gas 上限不能低于 10 万，回调执行失败也照样收费。

### 部署顺序为什么是「先 Reactive → 再 Callback → 再 setRecipient」？

这是一个「先有鸡还是先有蛋」的问题：

- 回调合约在部署时就要写死 Reactive 合约的地址（`_CALLBACK_SENDER` 是 immutable，部署后不能改，这样更安全）；
- Reactive 合约又要知道回调合约的地址，才能把回调发过去。

解决办法：先部署 Reactive 合约（暂不填接收方）→ 再部署回调合约（填入 Reactive 地址）→ 最后回到 Reactive 合约调用 `setRecipient` 补上接收方。

### 三个关键认知

1. **三笔交易是异步的，不保证同时成功**。Tx3 失败了，Tx1 也不会回滚。设计时要考虑「回调没送到」和「回调到达时情况已经变了」这两种情况。
2. **端到端延迟 = 源链出块 + Reactive 观察并出块 + 目标链出块**。速查表里的实测是 10 到 60 秒。赛道 1 要你测的就是这个。
3. **「链上能查到三笔交易」才算跑通**，因为每一步都可能静默失败：订阅没匹配上、合约欠费、用了旧的 Proxy 地址等等。FAQ 第 6、7 题就是按这三步依次排查的。

## 7️⃣ 跨链套利

**结论**：同一种资产在两条链的去中心化交易所（DEX）上价格不同时，在便宜的链上买、在贵的链上卖，赚中间的差价。价差之所以存在，是因为各条链的交易池各自定价、互不知情，而把价格拉平需要时间和成本。套利者就是负责「拉平」的人。

### 为什么会出现价差？

Uniswap 这类 DEX 用自动做市（AMM）定价，最简单的规则是 `x × y = k`：池子里 ETH 和 USDC 的数量比例，就决定了价格。

- 有人在 Base 上大单买入 ETH → Base 池子里的 ETH 变少 → Base 上的 ETH 价格上涨。
- Arbitrum 上的池子完全不知道这件事，价格不变。
- 同一条链上的价差，几秒内就会被套利机器人抹平，因为一笔交易里就能完成买和卖。但跨链的价差要横跨两条链去拉平，更慢、更难，所以它存在的时间更长、幅度更大。

根本原因就是第 1 节讲的：流动性碎片化，加上链和链之间不能直接通信。

### 怎么做？

```
Base 上     1 ETH = 3,000 USDC
Arbitrum 上 1 ETH = 3,030 USDC      价差 1%

① 在 Base 上用 3,000 USDC 买入 1 ETH
② 在 Arbitrum 上卖出 1 ETH，得到 3,030 USDC
净利 = 30 USDC − 两边的 gas − 两边的滑点 − 两边的交易手续费
```

| 做法 | 过程 | 问题 |
|---|---|---|
| 经过跨链桥（慢） | 在 Base 买入 ETH → 通过桥转到 Arbitrum → 卖出 | 过桥要几分钟到几天，价差早就没了，中间还要承担价格波动 |
| 两边提前备好资金（专业做法） | 在两条链上各存一些 USDC 和 ETH。发现价差后**同时**在两边各下一单，之后再找时间通过桥把两边的资金重新调平 | 需要更多本金，但抓住了时效 |

**用 Reactive 怎么做**：

- 订阅两条链上交易池的 `Sync` 或 `Swap` 事件（池子价格一变就会发出这些事件）；
- 在 `react()` 里根据池子储备算出两边价格；
- 价差超过阈值，就分别向两条链发回调，一边买、一边卖。

这正是赛道 1「Every Second Counts」的典型题目。

### 为什么不是稳赚

- **不保证两边同时成交**：两边是两笔独立交易，可能一边成交、一边失败，你手上就剩下一笔没对冲的仓位。开营 PPT 也专门强调了「回调不是原子操作」。
- **速度竞争**：别人的机器人比你快，等你下单时价差已经没了。所以赛道 1 要看延迟数据。
- **被抢跑**：你的交易在内存池里被别人看到，对方抢先成交（MEV）。
- **成本吃掉利润**：gas、滑点、过桥费加起来，可能把利润全部吃掉。

黑客松看的是机制本身，不承诺收益，全程只用测试网。

## 8️⃣ 巨鲸动向和聪明钱

**结论**：两者都是**利用区块链账本完全公开**来做的链上数据分析。巨鲸看的是「钱多」，聪明钱看的是「历史上赚得多」。

| | 巨鲸（Whale） | 聪明钱（Smart Money） |
|---|---|---|
| 定义 | 持有某种资产数量巨大的地址，比如交易所、早期持有者、机构、项目方 | 历史上交易胜率高、经常能提前买入的地址，比如专业交易团队、投资机构、掌握内部信息的人 |
| 判断依据 | 余额规模 | 历史表现 |
| 为什么值得关注 | 一笔交易就能影响价格和流动性 | 他们可能有信息优势，跟着看能早一步 |
| 典型信号 | 大额转入交易所（可能要卖）；从交易所提出（可能打算长期持有）；项目方地址解锁后转出 | 提前买入某个新币；大量加仓或清仓 |
| 常用工具 | Whale Alert、Etherscan | Nansen、Arkham、Dune 数据看板（这些工具会给地址打标签） |

- **为什么能看到**：链上每笔转账都公开可查（见第 3 节）。地址本身是匿名的，但根据它和交易所、已知项目之间的往来，可以推测出身份，给它打上标签。
- **局限**：标签只是推测；巨鲸会拆成很多小地址来掩护；也有人故意制造「巨鲸买入」的假象，诱导别人跟单。

### 和本营的联系：赛道 2 的入门题「大额转账监控」

用 Reactive 可以这样做：

- 订阅 USDC 合约的 `Transfer(address indexed from, address indexed to, uint256 value)` 事件对应的 topic0。
- ⚠️ 注意：`value` 没有标 `indexed`，它在 `data` 里，**订阅时没法按金额过滤**。只能在 `react()` 里解出金额再判断，不够大就 `return`。
- 但这样一来，每一笔 USDC 转账都会触发 `react()` 并扣费，主网上 USDC 转账非常多，费用会很高。更好的做法是用 topic1 或 topic2 只盯特定的巨鲸地址（比如 `from` 等于某个地址），先让订阅帮你做一轮粗过滤。这就是第 6 节「订阅做粗过滤，`react()` 做细判断」的实际用法。
- 条件满足后，回调到目标链上的一个「告警记录」合约，再由链下前端或机器人读取它、发出通知。
