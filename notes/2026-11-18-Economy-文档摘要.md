# Economy & System Interactions 文档摘要

> 📅 整理日期：2026-11-18 ｜ 适用版本：Reactive **Omni**（2026-10-28 主网迁移后）｜ 依赖：`reactive-lib-omni` v0.1.0、Solidity `^0.8.29`
>
> `AbstractPayer` 等源码摘自 `starter/lib/reactive-lib-omni`；其余示例代码为便于理解自行编写。

---

## 🎯 一句话结论

**Reactive 侧（REACT 付费给系统合约）和目标链侧（原生币付费给 Callback Proxy）用的是同一套记账逻辑：只要 debt > 0，合约就被拉黑、静默停止；失败和 revert 照样全额收费。** 充值首选 `depositTo(目标合约)`，它不需要目标合约配合，还能救活已欠费的合约。

### 五条核心规则

| # | 规则 | 不遵守的后果 |
|---|---|---|
| 1 | **两边都要充值**：Reactive 合约用 REACT，回调合约用目标链原生币（Sepolia 上是 ETH） | 任一侧欠费，该侧停止服务 |
| 2 | 欠费后用 `depositTo(addr)` 恢复 | 直接转账给合约**不会自动还债**，钱可能被"困住" |
| 3 | **不要**直接把 REACT 转给系统合约 | 记到的是**你自己的地址**，不是你的合约 |
| 4 | `react()` 里过滤用 `return`，不要 `revert` | revert 照样全额扣费，持续 revert 会把钱烧光 |
| 5 | 回调 `gasLimit` ≥ 100,000，并为 Proxy 的记账开销预留余量 | 低于 100k 直接被忽略；余量不够则 `InsufficientGas` |

## 1️⃣ 三个数字：Balance / Reserves / Debt

| 值 | 存在哪 | 含义 |
|---|---|---|
| **Balance（余额）** | 合约自己 | 合约可自由支配的钱 |
| **Reserves（储备）** | 系统合约 / Callback Proxy | 预付的手续费额度，**只能用来付费** |
| **Debt（债务）** | 系统合约 / Callback Proxy | 已产生但未支付的费用 |

三者之间的规则：

- 扣费时**先消耗 Reserves**，不够才产生 Debt。
- 充值（deposit）时**先还 Debt**，剩下的才进 Reserves。
- 因此一个合约**不会同时有 Reserves 和 Debt**。
- Balance 独立于两者：直接转账只会增加 Balance，**既不产生 Reserves，也不还 Debt**。

> ⚠️ **任何 Debt 都会阻断执行**：不是"钱不够才停"，而是"欠一分钱就停"。系统合约不再调用 `react()`，Callback Proxy 也不再投递回调。

## 2️⃣ 一笔 Reactive 交易的生命周期：`trigger()` 六步

每笔 Reactive 交易都经过系统合约的 `trigger()`：

```
01. Debt Check        合约有欠费？→ 直接 revert（不消耗合约的 gas，所以表现为"静默不响应"）
      │
02. Snapshot Gas      记录执行前的 gasleft()
      │
03. Execute react()   把 LogRecord 转发给你的合约（revert 会被捕获并记录，流程继续）
      │
04. Calculate Cost    (extraGas + gasUsed) × adjustedGasPrice
      │
05. Charge Contract   从 Reserves 扣；不够则调用合约的 pay()；仍不够 → 记 Debt → 停止服务
      │
06. Kickback          把扣到的费用转给 tx.origin（发出这笔交易的验证者）
```

从这六步可以推出两个关键行为：

| 现象 | 原因 |
|---|---|
| 欠费合约"安静地不工作"，而不是报错 | 第 1 步就检查债务，还没执行任何逻辑 |
| `react()` revert 了还被扣费 | 第 3 步的 revert 被捕获（记为 `ReactiveContractReverted`），照样走到第 5 步 |

> 💡 手续费**不沉淀在系统合约里**，直接付给干活的验证者（`tx.origin`）。

## 3️⃣ 费用模型

Reactive 交易和回调**共用同一个公式**，费用在执行的同一笔交易里收取，付给该交易的发起者（验证者）：

$$
fee = p_{base} \cdot C \cdot (g_{used} + K)
$$

| 符号 | 含义 | 来源 |
|---|---|---|
| $p_{base}$ | `max(tx.gasprice, block.basefee)` | 链上实时 |
| $C$ | 价格系数 | `_gasPriceCoeffPer1000 / 1000` |
| $g_{used}$ | 实际消耗的 gas | 执行结果 |
| $K$ | 固定 gas 附加费 | `_extraGas` |

### 默认值（Reactive 侧系统合约）

| 参数 | 初始值 | 说明 |
|---|---|---|
| `_gasPriceCoeffPer1000` | `1000`（即 C = 1） | owner 可改 |
| `_extraGas` | `100,000` gas | owner 可改 |
| `_maxChargeGas` | `50,000` gas | 不参与计费，只限制 `pay()` 可用的 gas |

> 🧮 推论：K = 100k 对小合约影响很大。一次只消耗 30k gas 的 `react()`，按 `(30k + 100k) = 130k` gas 计费。**每一次触发都有约 100k gas 的固定成本**，Cron 订阅、订阅过宽时尤其要注意。

Callback Proxy **没有默认值**，每条目标链部署时单独配置，必须直接读：

```bash
# Reactive 侧
cast call $SYSTEM_CONTRACT_ADDR "_gasPriceCoeffPer1000()" --rpc-url $REACTIVE_RPC | cast to-dec
cast call $SYSTEM_CONTRACT_ADDR "_extraGas()"             --rpc-url $REACTIVE_RPC | cast to-dec
cast call $SYSTEM_CONTRACT_ADDR "_maxChargeGas()"         --rpc-url $REACTIVE_RPC | cast to-dec

# 目标链侧（每条链都可能不同）
cast call $CALLBACK_PROXY_ADDR "_gasPriceCoeffPer1000()" --rpc-url $DESTINATION_RPC | cast to-dec
cast call $CALLBACK_PROXY_ADDR "_extraGas()"             --rpc-url $DESTINATION_RPC | cast to-dec
cast call $CALLBACK_PROXY_ADDR "_maxChargeGas()"         --rpc-url $DESTINATION_RPC | cast to-dec
```

### 失败照样收费

| 情况 | 记录的事件 | 是否收费 |
|---|---|---|
| `react()` revert | `ReactiveContractReverted` | ✅ 全额 |
| 回调执行失败 | `CallbackFailure` | ✅ 全额 |
| 回调目标地址**没有代码** | — | ❌ 唯一例外：在扣费前就被拒绝 |

---

## 4️⃣ Gas 限制

| 限制 | 数值 | 说明 |
|---|---|---|
| Reactive 交易 gas 上限 | **900,000** | `react()` 不能做太重的计算 |
| 回调最低 gasLimit | **100,000** | 低于此值的回调请求**直接被忽略**（不报错） |
| 回调实际可用 gas | `gasLimit − _extraGas − _maxChargeGas`（约） | Proxy 先为自身记账和 `pay()` 预留 gas，只把剩余部分转发给目标合约；预留都不够时以 `InsufficientGas` 失败 |

> ⚠️ 设置回调 `gasLimit` 时，要用**目标函数实际需要的 gas + 目标链 Proxy 的 `_extraGas` + `_maxChargeGas`** 来估算，不要只写 100,000 卡底线。

## 5️⃣ 给 Reactive 合约充值

两条路，区别在钱"放在哪"：

| 方式 | 钱进哪里 | 用途限制 | 能否自动还债 | 适用场景 |
|---|---|---|---|---|
| `SYSTEM.depositTo(合约)` | 系统合约中的 **Reserves** | 只能付手续费 | ✅ 先还债再存 | 首选；救活欠费合约（包括别人的合约） |
| 直接转账给合约 | 合约自己的 **Balance** | 合约可自由支配 | ⚠️ 只在扣费时经 `pay()` 自动付，或手动 `coverDebt()` | 希望钱留在合约控制下 |

### 5.1 `depositTo()`：存入 Reserves（推荐）

```bash
cast send --rpc-url $REACTIVE_RPC --private-key $REACTIVE_PRIVATE_KEY \
  $SYSTEM_CONTRACT_ADDR "depositTo(address)" $REACTIVE_CONTRACT_ADDR --value 1ether
```

- 由**调用者**出钱，给**任意合约**充值；先还 Debt，剩余进 Reserves。
- **不需要目标合约配合**，所以也是救活"欠费卡死的第三方合约"的方法。

> ⚠️ **一定要传目标地址**：直接把 REACT 转给系统合约，记账到的是**发送者自己**。EOA 这样转钱，等于充给了一个永远不会执行的地址。

### 5.2 直接转账 + `pay()` / `coverDebt()`

```bash
cast send $REACTIVE_CONTRACT_ADDR --rpc-url $REACTIVE_RPC --private-key $REACTIVE_PRIVATE_KEY --value 1ether
```

- **部署时附带 `--value`** 只有在构造函数是 `payable` 时才行；基类构造函数不是 `payable`，自己不加就会 revert。
- Balance 本身不会还任何债，要靠以下两种方式交给系统合约：

| 方式 | 何时发生 | 说明 |
|---|---|---|
| **自动：`pay()`** | 扣费时 Reserves 为空，系统合约调用合约的 `pay(amount)` 要钱 | 继承自 `AbstractPayer`；在扣费的**同一笔交易**里结清，合约**不会被拉黑** |
| **手动：`coverDebt()`** | 已经欠费后，有人调用合约暴露的 `coverDebt()` | `_coverDebt()` 是 `internal`，**基类不暴露**，需自己写外部包装 |

`AbstractPayer` 源码（`reactive-lib-omni/src/base/AbstractPayer.sol`，节选加注释）：

```solidity
abstract contract AbstractPayer is IPayer {
    error NotAuthorized(address sender_, address provider_);
    error InsufficientFunds(uint256 required_, uint256 available_);
    error TransferFailed();

    // Reactive 合约里是系统合约，回调合约里是 Callback Proxy
    IPayable public immutable _SERVICE_PROVIDER;

    receive() virtual external payable {}   // 允许直接转账进来

    // 自动付费：只有服务方（系统合约 / Proxy）能调用
    function pay(uint256 amount_) external onlyServiceProvider {
        _pay(payable(msg.sender), amount_);
    }

    // 手动还债：查询当前债务并全部付清；internal，需要合约作者自行暴露
    function _coverDebt() internal {
        uint256 amount = _SERVICE_PROVIDER.debt(address(this));
        _pay(payable(_SERVICE_PROVIDER), amount);
    }

    function _pay(address payable recipient_, uint256 amount_) internal {
        if (address(this).balance < amount_) {
            revert InsufficientFunds(amount_, address(this).balance);   // 余额不足直接 revert
        }
        if (amount_ > 0) {                                               // 债务为 0 时什么也不做
            (bool success,) = payable(recipient_).call{ value: amount_ }(new bytes(0));
            if (!success) revert TransferFailed();
        }
    }
}
```

在你的合约里暴露 `coverDebt()`（官方推荐写法）：

```solidity
/// @notice Settles outstanding debt from this contract's own balance.
function coverDebt() external {
    _coverDebt();
}
```

- 需要限制调用者就加 `onlyOwner` 等权限控制（**基类不提供 `onlyOwner`，需自行实现**）。
- 公开版本对服务第三方的合约很有用：任何人都可以给合约打钱再调用它来重启服务。
- 完全不写这个包装也是合法选择，但那样欠费后就**只能走 `depositTo()`**。

```bash
cast send --rpc-url $REACTIVE_RPC --private-key $REACTIVE_PRIVATE_KEY $REACTIVE_CONTRACT_ADDR "coverDebt()"
```

> ⚠️ **`pay()` 的 gas 上限是 `_maxChargeGas`**：自定义的 `pay()` 超出预算或余额不足，会触发 `PaymentFailure` 事件、债务保留。**不要在 `pay()` 里写复杂逻辑。**
>
> ⚠️ **欠费合约收到的直接转账可能被困住**：如果合约没暴露任何"从余额付给系统合约"的方法，这笔钱谁都没法拿去还债。不确定时一律用 `depositTo()`。

## 6️⃣ 合约状态：active / inactive

可以在 Reactscan（测试网：https://lasna.reactscan.net）查看。

| 状态 | 含义 | 触发事件 |
|---|---|---|
| `active` | 正常执行 | Debt 回到 0 时发出 `WhitelistContract`，恢复服务 |
| `inactive` | 有未结清债务 | Debt 从 0 变为正数时发出 `BlacklistContract`，停止服务 |

> 💡 在扣费的同一笔交易里通过 `pay()` 结清的合约**根本不会被拉黑**。所以"合约里留足余额 + 默认的 `pay()`"也是一种不断服的方式。

## 7️⃣ 给回调合约充值

规则与 Reactive 侧完全相同：`AbstractCallback` 继承 `AbstractPayer`，`pay()` / `_coverDebt()` 行为一致，欠费即停止接收回调。

> 📌 **回调合约用目标链原生币付费**（Ethereum 上是 ETH、BNB Chain 上是 BNB……），**不是 REACT**。

```bash
# 方式一：通过 Callback Proxy 存入 Reserves（推荐）
cast send --rpc-url $DESTINATION_RPC --private-key $DESTINATION_PRIVATE_KEY \
  $CALLBACK_PROXY_ADDR "depositTo(address)" $CALLBACK_CONTRACT_ADDR --value 0.1ether

# 方式二：直接转账给回调合约，再手动结清（前提：合约暴露了 coverDebt()）
cast send $CALLBACK_CONTRACT_ADDR --rpc-url $DESTINATION_RPC --private-key $DESTINATION_PRIVATE_KEY --value 0.1ether
cast send --rpc-url $DESTINATION_RPC --private-key $DESTINATION_PRIVATE_KEY $CALLBACK_CONTRACT_ADDR "coverDebt()"
```

## 8️⃣ 查询命令速查

两边用同一套查询：Reactive 合约查**系统合约**（`REACTIVE_RPC`），回调合约查 **Callback Proxy**（`DESTINATION_RPC`）。

先准备环境变量（测试网示例，私钥只用测试钱包，**不要提交 `.env`**）：

```bash
export REACTIVE_RPC=https://lasna-rpc.rnk.dev/
export SYSTEM_CONTRACT_ADDR=0x8888888888888888888888888888888888888888
export DESTINATION_RPC=<Sepolia RPC>
export CALLBACK_PROXY_ADDR=0xAa14d9Cd0f788Ca23d11805986C1d8bd035D23b4   # Ethereum Sepolia
```

| 查什么 | Reactive 侧 | 目标链侧 |
|---|---|---|
| Balance | `cast balance $REACTIVE_CONTRACT_ADDR --rpc-url $REACTIVE_RPC` | `cast balance $CALLBACK_CONTRACT_ADDR --rpc-url $DESTINATION_RPC` |
| Debt | `cast call $SYSTEM_CONTRACT_ADDR "debt(address)" $REACTIVE_CONTRACT_ADDR --rpc-url $REACTIVE_RPC \| cast to-dec` | `cast call $CALLBACK_PROXY_ADDR "debt(address)" $CALLBACK_CONTRACT_ADDR --rpc-url $DESTINATION_RPC \| cast to-dec` |
| Reserves | `cast call $SYSTEM_CONTRACT_ADDR "reserves(address)" $REACTIVE_CONTRACT_ADDR --rpc-url $REACTIVE_RPC \| cast to-dec` | `cast call $CALLBACK_PROXY_ADDR "reserves(address)" $CALLBACK_CONTRACT_ADDR --rpc-url $DESTINATION_RPC \| cast to-dec` |
| 服务方是谁 | `cast call $REACTIVE_CONTRACT_ADDR "_SERVICE_PROVIDER()" --rpc-url $REACTIVE_RPC` | `cast call $CALLBACK_CONTRACT_ADDR "_SERVICE_PROVIDER()" --rpc-url $DESTINATION_RPC` |

- `debts(address)` 是旧别名，返回值相同；新代码用 `debt(address)`（属于 `IPayable` 接口）。
- `_SERVICE_PROVIDER()` 是在**付费方合约自己**上调用的：Reactive 合约返回系统合约，回调合约返回 Callback Proxy。可用来确认回调合约的 Proxy 有没有填对。

### 追踪回调：`getCallbacks()`

系统合约按**发起回调的 Reactive 交易哈希**记录每一笔回调；一笔 Reactive 交易可以发出多个回调，所以返回数组：

```bash
cast call $SYSTEM_CONTRACT_ADDR \
  "getCallbacks(uint256)((uint256,address,uint256,uint256,uint256,bytes)[])" \
  $REACTIVE_TX_HASH --rpc-url $REACTIVE_RPC
```

| 字段（按顺序） | 含义 |
|---|---|
| `uint256` | 区块号 |
| `address` | 发起回调的 Reactive 合约 |
| `uint256` | 该回调在这笔交易中的序号 |
| `uint256` | 目标链 Chain ID |
| `uint256` | 目标链上的交易哈希 |
| `bytes` | 目标合约返回的错误数据；**为空表示成功** |

> 💡 记录由验证者在投递后写入，**空数组表示"还没记录"，不代表失败**。稍等片刻再查。这条命令很适合黑客松里证明"三笔交易都跑通了"。

## 9️⃣ 排障速查

| 现象 | 先查什么 | 处理 |
|---|---|---|
| 源链有事件，Lasna 上没有 reaction | Reactive 合约的 `debt` | `depositTo` 充值后应出现 `WhitelistContract` |
| 有 reaction，但目标链没有回调 | 回调合约的 `debt`；回调 `gasLimit` 是否 < 100k | 在目标链 Proxy 上 `depositTo`；调大 `gasLimit` |
| 回调交易存在但失败 | `getCallbacks` 的 `err` 字段 | 检查 Proxy 地址、`_CALLBACK_SENDER`、gas 余量 |
| 充了钱还是 inactive | 是不是直接转给了合约或系统合约 | 改用 `depositTo(合约地址)`；或调用合约的 `coverDebt()` |
| 部署时带 `--value` 失败 | 构造函数是否 `payable` | 加 `payable`，或部署后再 `depositTo` |
| 钱烧得很快 | 是否 `react()` 经常 revert、订阅过宽、Cron 间隔太短 | 过滤用 `return`；收窄订阅；加长间隔 / 加暂停开关 |

## ✅ 资金自查清单

- [ ] Reactive 合约（Lasna）有 REACT：Reserves 或 Balance
- [ ] 回调合约（目标链）有原生币：Reserves 或 Balance
- [ ] 充值用 `depositTo(合约地址)`，不直接转给系统合约 / Proxy
- [ ] 想部署时充值就给构造函数加 `payable`
- [ ] 需要手动还债就暴露 `coverDebt()`，并决定是否加权限控制
- [ ] 没有自定义复杂的 `pay()`
- [ ] `react()` 不 revert；回调 `gasLimit` ≥ 100k 且已预留 Proxy 开销
- [ ] 上线后用 `debt` / `reserves` / `getCallbacks` 巡检一次
