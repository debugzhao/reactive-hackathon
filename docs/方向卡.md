# 🧭 方向卡：即时结算提款队列（Instant-Settle Withdrawal Queue）

> Reactive Omni Buildathon · 2026-11-25 · 详细设计见 [即时结算提款队列-产品与技术方案.md](即时结算提款队列-产品与技术方案.md)，代码见 [`queue-vault/`](../queue-vault/)

## 1. 一句话

**监听** Base Sepolia 上借贷池 `MockPool` 的还款事件 `Repaid`，以及金库 `QueueVault` 的队列快照 `LiquiditySnapshot`；**一旦**池里出现的流动性够付队首的排队提款，**就在** Base Sepolia 上回调 `QueueSettler`，先把这笔流动性从池里取回金库，再按 FIFO 兑付排队的用户。整个过程在几秒内完成。

## 2. 赛道

**赛道 1：Every Second Counts**（Base Sepolia ↔ Reactive Lasna）

**为什么需要 1 秒级反应**：

- **池里的流动性先到先得**。借款人一还款，池里刚出现的钱谁先取走就是谁的，其他存款人的机器人也在抢。
- **慢一步的代价很具体**：被别人抢走之后，排队用户要等**下一次还款**，可能是几小时甚至几天。
- **还款进的是第三方池子，金库自己的代码一行都不会执行**，必须有一个能看到事件、并能立刻上链的角色。
- **用实验量化**：让一个对手机器人在还款后 T 秒（T = 3s / 10s / 30s）取走池里的全部资金，对比 Reactive Omni（实测）、轮询机器人（实测）、旧版约 7 秒出块（推算）三种方案的**抢到率**，同时报告端到端延迟的中位数和 P95。

## 3. 目标用户和真实场景

| 用户 | 场景 | 现在怎么解决 | 问题 |
|---|---|---|---|
| 收益金库的存款人 | 金库把钱存在 Aave / Morpho 这类资金池里生息；池子利用率接近 100% 时取不出钱，只能排队 | 反复手动重试，或者等金库管理人处理 | 偶尔出现的流动性，常常被别人的机器人先取走 |
| 金库管理人 | 想多放贷赚收益，又不想让用户提款卡住 | 自己写 keeper 机器人，跑服务器，在服务器上放热钱包私钥 | 要运维，私钥有被盗风险，机器宕机时队列就卡住 |
| 集成方（持有金库份额的协议） | 需要退出路径可预期 | 只能按最坏的退出时间做风控 | 退出时间不确定 |

**Reactive 带来的改变**：不需要服务器，不需要托管私钥；FIFO 顺序和兑付规则写在合约里，不能插队；结算函数 `settleQueue` 不设权限，任何人都能调用，作为 Reactive 不可用时的兜底。

## 4. 最小 Demo（第 2 周结束前必须跑通的链路）

```
① Base Sepolia   用户 requestRedeem → 锁定价格、销毁份额、进入 FIFO 队列
② Base Sepolia   借款人 MockPool.repay(2,500) → emit Repaid（钱进的是池子，不是金库）
③ Lasna          QueueReactive.react() 判断“可取回的流动性 ≥ 门槛”→ requestCallbackV_1_0
④ Base Sepolia   QueueSettler.onSettle → vault.settleQueue：从池里取回缺口 → 按 FIFO 兑付 → emit ReactiveSettled
```

**验收标准**：

- 区块浏览器上能查到 `Repaid → react → ReactiveSettled` 三笔交易。
- 用户 USDC 到账，并附上端到端延迟。
- 跑完至少一组抢流动性实验（对手 T 取 3s / 10s / 30s）。
